## What is fixed

The authored recipe preserves the accepted runtime command and tuning: B12X attention and linear backends, InstantTensor, a graph cap of 16 with capture sizes `1, 2, 3, 4, 8, 12, 16`, GPU utilization `0.81`, four sequences, and an 8,192-token batch budget. It does not present these constants as a general tuning matrix.

The LWS target is **verified** against the recorded live acceptance. The Docker target uses the same engine definition and is rendered and syntax-checkable, but remains **not yet runtime-validated** on two free hosts.

:::caution[Allocator units are not physical devices]
Kubernetes extended-resource counts are values published by the cluster's device plugins. A site may advertise more allocator units than physical hardware. The beginner path requests one GPU and one RDMA unit per rank; experienced operators must match the generated requests to their own allocator policy.
:::

## Two traffic paths

The rank-zero API receives requests on port `8888`. The second rank is headless and participates in tensor-parallel collectives over the configured secondary network. Control and probe traffic stays on the primary pod network; the Multus attachment carries collective traffic.

## Before applying output

- For Kubernetes, complete the <a href={`${import.meta.env.BASE_URL}guides/cluster-prerequisites/`}>cluster prerequisite checklist</a> and confirm the NVIDIA runtime, LWS controller, CNI, Multus, and RDMA allocator are ready.
- For Docker, synchronize the model on both hosts before starting either serving container. Start rank zero first, then let the worker's rendezvous check succeed before its headless server starts.
- Stop a GB10 serving container gracefully with a 120-second timeout. Long kernel execution is not grounds for force-killing a GPU process.
- A digest-qualified latest image is newer, not equivalent to the validated recipe image. Selecting it changes the validation status shown by the generator.
